# アップデート情報 (/updates) に掲載する

CHANGELOG と同様に、**一般ユーザーが知るべき変更** はインスタンスの「アップデート情報」(`/updates`) にも掲載する。掲載は 1 件ごとに **全ローカルユーザーへ通知が配信される** ため、対象の見極めと粒度の集約が重要。

## 掲載する / しない の判定基準

**掲載する (一般ユーザーが知るべき情報):**

- 新機能の追加 (ユーザーが使えるもの)
- ユーザーから見える UI / 挙動の変更
- ユーザーが体感していた不具合の修正 (「〜できないことがあった」系)
- ユーザーの行動に影響する注意事項 (制限の追加、非互換な挙動変更、再ログインが必要 など)

**掲載しない (管理者・開発者のみ知ればよい情報):**

- 管理者 / モデレーター向け機能 (admin 画面・admin API・モデレーションツール)
- CI / インフラ / デプロイパイプラインの変更
- 内部リファクタリング・依存更新・パフォーマンス改善のうちユーザーが体感しないもの
- セキュリティ修正の内部詳細 (告知が必要な場合も詳細は伏せて影響と対処のみ)
- config 項目の追加などサーバー運用者向けの変更
- **まだ一般ユーザーが利用できない機能** — 外部サービスの審査待ち (例: Google OAuth アプリ検証)、管理者限定の先行公開、feature flag オフなど。コードがデプロイ済みでも利用可能になるまで掲載しない (前例: 2026-08-12 に配信アーカイブを掲載したが Google 審査未完了のため取り下げた)

迷ったら「CHANGELOG の該当エントリを読んだ一般ユーザーが、自分に関係あると感じるか」で判定する。関係ないなら載せない。

## タイミングと粒度

- **本番デプロイが完了し動作確認できてから** 掲載する (未反映の機能を告知しない)
- 1 機能 = 1 件が基本。小粒な修正が複数あるときは「◯◯アップデート: 改善まとめ」として **1 件に集約** する
- 連投しない。同一デプロイ由来の複数変更はできるだけまとめる (1 件 = 全ユーザー通知 1 回)

## 掲載方法

LAN 内からは認証不要エンドポイント `update-info/create-local` を使う (X-Forwarded-For 付き = 公開経路からのリクエストは拒否される。config `updateInfoLocalPost.allowedIps` で制御):

```bash
curl -X POST 'http://mi-host.msjp-local.org:3000/api/update-info/create-local' \
  -H 'Content-Type: application/json' \
  -d '{"title": "🔧 ◯◯アップデート: ...", "text": "本文"}'
```

管理画面 (admin/update-info/create、要モデレーター権限) からも投稿できる。

## 文面の流儀 (既存エントリに合わせる)

- タイトル: 絵文字 + 「◯◯アップデート: 概要」または「◯◯を追加しました」。既存例: 「🎞️ 配信機能アップデート: 配信アーカイブを追加しました」
- 本文: `**■ 見出し**` + 箇条書き。ユーザーの言葉で書く (クラス名・内部用語・コミットハッシュを出さない)
- 注意事項は本文末尾に `※` または `**■ 注意事項**` でまとめる
- 過去分の後追い掲載なら「(7月19日から提供中のお知らせです)」のように提供開始時期を明記する
- 文字数上限: title 256 / text 8192

## CHANGELOG との対応

`CHANGELOG.md` の `## Unreleased` に追記した Client / Server エントリのうち、上の判定基準で「掲載する」に該当するものが対象。CHANGELOG は開発履歴 (全変更)、アップデート情報はユーザー告知 (選別 + 翻訳) という役割分担。
